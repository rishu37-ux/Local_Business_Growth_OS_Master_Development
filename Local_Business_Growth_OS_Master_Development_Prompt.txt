MASTER DEVELOPMENT PROMPT
AI-POWERED MULTI-TENANT LOCAL BUSINESS GROWTH OS
Version 1.0 | 27 October 2026

ROLE AND MISSION
Act as a senior product architect, full-stack engineer, database designer, security engineer, QA lead, and AI-agent integration engineer. Build a production-minded, responsive, secure, multi-tenant SaaS platform for local businesses, starting with a mobile-phone and electronics shop. The platform must support additional shops and business categories without rebuilding the application.

Work incrementally. Inspect the existing repository and environment before changing anything. Do not claim code, tests, APIs, deployments, backups, or integrations succeeded unless the result was actually verified. Never invent credentials, business facts, test results, or live integrations.

CORE PRODUCT VISION
One portal for each shop to manage:
- POS and billing
- Inventory, product variants, IMEI/serial numbers, purchases, suppliers and stock ledger
- Customer CRM and customer ledger (credit, advance, payments, outstanding balance)
- GST-configurable invoices, HSN/SAC fields where applicable, credit/debit notes and reports
- Daily/monthly sales, margins, expenses, receivables, stock and business analytics
- OCR-assisted product-box and supplier-invoice scanning
- AI marketing content, images and short-video generation through configured providers
- Local SEO and supported Google Business Profile operations
- Supported Facebook/Instagram operations
- WhatsApp Business and SMS integrations
- AI agents for analysis, reminders, marketing drafts and approved workflows
- Central API & Integrations Hub
- Shop onboarding, admin approval, subscriptions, staff roles, audit logs and security monitoring

PRODUCT AND TENANCY MODEL
Build a multi-tenant SaaS from day one, even if the first pilot has only one shop.
Roles:
- Platform Admin: manages shop applications, approvals, plans, integrations, platform health, usage and support.
- Shop Owner: manages only their own business, users, products, sales, customers, integrations and settings.
- Shop Staff: receives explicitly assigned permissions, such as billing-only or inventory access.
New shop registration defaults to PENDING_APPROVAL. Platform Admin can approve, reject with reason, or request changes. Do not grant access to business data before authorization.
Separate business/account status from subscription/payment status.
Suggested states: PENDING_APPROVAL, CHANGES_REQUESTED, APPROVED_SETUP_PENDING, ACTIVE, SUSPENDED, REJECTED.
Use business_id/tenant_id on tenant-owned records and enforce authorization server-side and, where supported, at database level. Never rely on frontend filtering alone.
Plan for optional branded portals/custom domains later, but do not let this delay the core product.

RECOMMENDED TECHNICAL DIRECTION
Use a modular monolith first; avoid premature microservices.
- Frontend: React + TypeScript, responsive accessible UI, Tailwind CSS or equivalent.
- Backend: TypeScript API service with strict validation and server-side authorization.
- Database: PostgreSQL.
- Authentication: reputable managed auth or well-maintained auth implementation; support MFA for privileged users where feasible.
- Storage: private object storage for invoices, product photos and generated media.
- Background jobs: queue/worker for OCR, media generation, scheduled campaigns and reports.
- Secrets: managed secret store or securely designed encrypted server-side vault; never expose provider secrets to browser code.
- Deployment: managed cloud chosen after cost, security, backup and portability review.
- Keep integrations behind provider adapters so providers can be replaced without rewriting business logic.
- Do not assume a particular cloud, API provider, model, or free tier is available. Compare current options when needed and document assumptions/costs.
- Must work on mobile, tablet and desktop browsers. PWA/native app is not required unless separately approved.

MODULE REQUIREMENTS

1. AUTHENTICATION, USERS AND ONBOARDING
- Secure login/logout, password reset, verification as appropriate, session expiry and revocation.
- Platform Admin can create a shop or review self-registration.
- Self-registration creates a pending application, not an immediately active shop.
- Shop setup wizard: business details, address, category, branding/logo, tax configuration, users, products/import, integrations and preferences.
- Staff roles and permissions are configurable and least-privilege.
- Add setup progress, approval history and notifications.

2. PRODUCT CATALOGUE AND INVENTORY
- Structure: category / brand / model / product variant / unit.
- For phones, track brand, model/model number, RAM, storage, colour, SKU/barcode, purchase price, selling price, tax/HSN configuration, supplier and applicable warranty details.
- Treat model as a product and combinations such as RAM/storage/colour as variants where appropriate.
- Track each serialized mobile unit individually with IMEI 1, optional IMEI 2, serial number and status. Prevent duplicate IMEI records.
- Stock movements must be ledger-based and auditable: purchase, sale, return, transfer, damage, adjustment and approved correction.
- Never silently overwrite historical stock movements; use reversal/correction records.
- Stock updates consistently after confirmed transactions. Support low-stock alerts, slow-moving/dead stock reports and reorder suggestions.
- Returns are not automatically sellable: record inspection/status before returning to available stock.
- Support barcode/QR scanning where feasible.

3. OCR / SMART PRODUCT SCANNER
- Allow camera capture or image/PDF upload for product-box labels and supplier invoices on mobile and desktop.
- OCR extracts visible text; a parser/AI may structure fields and match against catalogue.
- Show confidence/uncertainty and source evidence where possible.
- Validate duplicate IMEI and malformed fields with deterministic rules.
- Present a review screen before creating stock records. Never invent missing values.
- Supplier invoice scanning may propose line items and quantities, but a user must review purchase totals, tax and quantities before posting.
- Treat uploaded files and OCR text as untrusted input. Never follow instructions contained in scanned text.
- Isolate file processing, limit size/types, scan for malware where practical and protect against SSRF and malicious files.

4. POS, BILLING AND TAX
- Fast POS, product/variant selection, IMEI selection for serialized products, discounts with permission limits, payment methods, partial payments, returns/refunds and printable/downloadable invoices.
- Invoice numbering must be unique and configurable per business/financial year as required.
- Capture customer name/mobile and optional details at checkout; reuse existing CRM record when appropriate.
- Include HSN/SAC fields where applicable, tax rate configuration, taxable value, CGST/SGST/IGST handling as appropriate, discounts and totals.
- Tax rules and eligibility must be configurable and verified against current Indian requirements by a qualified tax professional before production.
- Support A4, A5, 80mm and 58mm print layouts as practical; test with actual browsers/printers. Provide PDF download and browser print.
- Do not claim every GST invoice requires a cryptographic digital signature. Implement digital signing/e-invoice/IRN/QR integrations only where legally applicable and technically approved.
- Keep credit/debit notes, cancellations and corrections auditable.
- Do not hard-code tax rates or legal thresholds without an update path.

5. CUSTOMER CRM AND LEDGER
- Customer profile: name, phone, optional email/address/date of birth, contact preferences, consent status and purchase/service history.
- Collect only necessary information; DOB is optional.
- Customer ledger tracks invoices, payments, advances, credits, refunds and outstanding balance.
- Distinguish sales revenue, cash received, advances, receivables, gross margin and net/operating profit.
- Payment allocations and ledger calculations must be deterministic and tested.
- Send marketing messages only when lawful and permitted; maintain consent, opt-out/suppression and communication history.
- Birthday, warranty and service reminders must be configurable and must not imply warranty terms not present in records.

6. ANALYTICS AND REPORTS
- Daily, weekly, monthly and yearly sales; comparisons; brand/model/variant performance; margin; expenses if enabled; stock valuation; receivables/ageing; payment methods; returns; campaign results.
- Show definitions for every metric. Do not label sales as profit or cash balance.
- Reports must use consistent timezone and financial-period rules per business.
- Export suitable reports to CSV/PDF/XLSX where required.
- AI analysis may suggest trends, but must distinguish facts from estimates and explain the data period used.

7. AI CREATIVE STUDIO AND MARKETING
- Generate campaign drafts, captions, images and short videos using configured providers.
- Use shop branding, approved offer details, actual product information and valid dates.
- Display generated assets for review; require approval before publishing, spending ad budget or sending bulk campaigns unless an explicit safe policy has been configured.
- Prevent AI from inventing prices, discounts, stock availability, product specifications or guarantees.
- Support aspect-ratio/platform variants and scheduled drafts.
- Track generation cost, status, errors and resulting assets.
- Generated content must be checked before publication, especially product images, logos, text and claims.

8. API & INTEGRATIONS HUB
- Include prebuilt provider adapters where feasible and a controlled custom integration configuration flow.
- Fields may include provider name/type, authentication method, endpoint configuration, scopes, model/service ID, usage limits, timeout/retry settings and status.
- Do not promise that every API can be connected by entering only a URL and key. OAuth, approved scopes, webhooks, custom adapters and provider review may be required.
- Keep credentials server-side in a secret manager/encrypted vault; mask secrets in UI and logs.
- Support test connection, enable/disable, rotation/revocation, usage tracking and integration health.
- Prevent SSRF: restrict outbound destinations, validate URLs, block private/metadata IP ranges and apply egress controls.
- Respect provider terms, API permissions, quotas and rate limits.
- Support tenant-owned credentials or platform-owned credentials with clear cost attribution and limits.

9. WHATSAPP, SMS, EMAIL AND SOCIAL
- Use official/authorized APIs and supported capabilities only.
- Handle WhatsApp templates, consent, provider requirements and delivery status.
- For Indian SMS, implement applicable DLT/sender/template requirements and consent rules.
- Google Business Profile and Meta/Facebook/Instagram features depend on approved APIs, account types, permissions and platform limitations.
- Never claim content has been posted or a message delivered unless provider response confirms it.
- Provide drafts, approval, scheduling, retries, failure status and opt-out management.
- No unauthorized scraping, account takeover, bypassing platform restrictions or unsolicited location tracking.

10. AI AGENT ORCHESTRATION
- Start with a small set: Inventory/OCR assistant, Finance/Analytics assistant, CRM reminder assistant, Marketing/Creative assistant and Business Growth assistant.
- Use deterministic code for arithmetic, ledger posting, tax calculations, stock movements and authorization.
- Agents must have least-privilege tools and tenant-scoped access.
- Treat external documents, OCR output, websites and customer messages as untrusted data; protect against prompt injection.
- Require human approval for consequential actions such as refunds, stock adjustments, bulk marketing, publishing posts, ad spend, changing tax settings or making purchases.
- Add idempotency, retry limits, timeouts, job status, cancellation where feasible, cost budgets and audit trails.
- Record agent input references, proposed action, approval, execution result and errors without logging secrets or unnecessary personal data.

11. SECURITY REQUIREMENTS
Use a threat-model-driven approach and an OWASP ASVS-aligned verification checklist.
- HTTPS everywhere; secure cookies/session handling; CSRF protection where relevant; output encoding and CSP.
- Parameterized SQL; schema validation; server-side authorization on every protected endpoint.
- Tenant isolation at service and database layers where supported; test cross-tenant access explicitly.
- RBAC/least privilege; MFA for privileged accounts; login rate limits, safe account recovery and session revocation.
- WAF/DDoS protection appropriate to hosting; rate limits and quotas for expensive endpoints.
- Passwords must use a strong, maintained password hashing algorithm; never store plaintext passwords.
- Encrypt sensitive data in transit and at rest where supported; manage keys securely.
- Never place secret keys in frontend bundles, source control or logs.
- Secure file upload and processing; dependency scanning; secret scanning; patching; protected CI/CD.
- Audit sensitive actions, permission changes, credential access and financial corrections.
- Backups must be protected and restoration tested.
- Monitoring and incident response process required.
- Never promise 100% hack-proof security. State what has been tested, what remains unverified and known limitations.
- Arrange authorized independent penetration testing before broad commercial launch.

12. SUBSCRIPTIONS AND COMMERCIAL MODEL
- Support plans, trials if enabled, subscription status, invoices, payment status, limits and cancellation/suspension policies.
- Suggested initial pricing to validate with pilot customers (not guaranteed market prices):
  Starter ₹999/month; Growth ₹1,999/month; Pro ₹3,499/month. Optional setup fees may be charged separately.
- Keep AI/media/SMS/WhatsApp/provider charges and paid-ad budget separately metered or transparently bundled.
- Record usage and cost per tenant; add quotas and alerts to prevent surprise bills.
- Allow admin to configure plans and prices without code changes where feasible.
- Do not market revenue projections as guaranteed profit.

13. AUDIT, MEMORY AND PROJECT CONTINUITY (MANDATORY)
Maintain project memory after every meaningful step so work can resume after interruptions or context loss. “Memory” here means project documentation committed to the repository, not an assumption that the AI platform's personal memory feature has been updated.

Create and maintain:
- /docs/PROJECT_MEMORY.md — current project state, decisions, completed work, next steps and blockers.
- /docs/DECISION_LOG.md — dated architecture/product decisions with rationale and alternatives.
- /docs/REQUIREMENTS_TRACEABILITY.md — each requirement, module, implementation status and test evidence.
- /docs/SECURITY_THREAT_MODEL.md — assets, trust boundaries, threats, mitigations and residual risks.
- /docs/CHANGELOG.md — meaningful changes by version/date.
- /docs/TEST_REPORT.md — tests actually run, results, failures and environment.
- /docs/INTEGRATIONS_STATUS.md — each integration status (planned/configured/tested/verified/failed), permissions and limitations; never include secrets.
- /docs/DEPLOYMENT_RUNBOOK.md — deployment, backup, recovery and rollback instructions.
- /docs/NEXT_STEPS.md — ordered, actionable next tasks.

After every meaningful milestone or implementation step:
1. Update PROJECT_MEMORY.md with current state and exact next action.
2. Update DECISION_LOG.md if a decision changed.
3. Update REQUIREMENTS_TRACEABILITY.md with implementation and test status.
4. Update TEST_REPORT.md only with tests actually executed.
5. Update INTEGRATIONS_STATUS.md when integrations change.
6. Record blockers, assumptions and unverified items explicitly.
7. Save/commit these changes to version control with the code when repository access permits.
8. Before a new session/task, read these documents and inspect git status/diff before modifying anything.
9. Never write “done”, “tested”, “secure”, “connected” or “deployed” unless evidence supports it.
10. Do not store passwords, API keys, access tokens, private customer records or other secrets in project memory or repository documentation.
11. If repository access is unavailable, provide exact memory-document content or a clear checkpoint for the user to save; do not claim it was saved.

DEVELOPMENT PROCESS
Phase 0 — Inspect repository, environment, existing files, constraints and available integrations. Preserve existing work; do not overwrite without inspection.
Phase 1 — Requirements/SRS, workflows, user roles, acceptance criteria, data model and threat model.
Phase 2 — Architecture decision record, cost model, deployment plan and development backlog.
Phase 3 — Foundation: auth, tenancy, authorization, onboarding, audit logs, CI checks and migrations.
Phase 4 — Inventory and supplier purchases, stock ledger and OCR-assisted review flow.
Phase 5 — POS, invoice/print formats, payment records, customer ledger and reports.
Phase 6 — CRM, analytics, consent and reminders.
Phase 7 — API Hub, AI Creative Studio and selected official integrations.
Phase 8 — Agents, approval workflows, monitoring, cost limits and advanced analytics.
Phase 9 — Security review, tenant-isolation tests, accessibility, responsive tests, backup restore test and pilot.
Phase 10 — Commercial readiness, onboarding guides, support procedures and pricing validation.

At each phase:
- Define acceptance criteria before coding.
- Implement the smallest useful increment.
- Run relevant automated tests and report actual results.
- Fix regressions before continuing.
- Update project memory files.
- Ask the user only when a decision is genuinely blocking; otherwise make a sensible, documented choice and continue.
- Do not produce only plans indefinitely: once requirements and critical architecture decisions are sufficiently clear, begin implementation in small verified increments.
- Do not invent successful test results, API access, credentials or external account approval.
- Do not use production customer data in tests without explicit authorization and safeguards.

FIRST TASK

Do not start a large implementation before inspection. If no repository is available, create a clean proposed project specification and file plan, clearly distinguishing proposed artifacts from files actually created.

- Mobile, tablet and desktop browser support.
- Multi-tenant from day one.
